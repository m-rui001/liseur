# STEM 书稿 → 带 LaTeX 公式的 EPUB：一条可复现的管线

> 这是 [Liseur 分支](../README.md) 的**另一半**。App 负责把公式画出来，本文讲
> 公式是**怎么进到书里**的：扫描版与数字版 STEM PDF → 正文 + LaTeX 源码 + 插图 →
> EPUB3 → 手机上带着一整库数学书。
>
> 管线代码不在本仓库里（目前在工作机 `E:\EPUB\` 下，脚本名一律照本文写法给出），
> 但设计、判据、实测数字都在这里，照着能重建。文中数字均取自 2026-09-20~22 的实测日志。

## 1. 问题陈述

手机和电子书阅读器上读 STEM 书，通常只有三种坏选择：

| 做法 | 坏在哪 |
|---|---|
| 直接读 PDF | 版面是为 A4 设计的。放大就一行只看得进五个字，重排后公式和图全部错位，翻页手势和文字选择抢同一根手指 |
| 公式转图片 | 保真，但**不可重排、不可搜索、不可复制**，放大就糊；一本 300 页的书会胖十倍 |
| 输出 MathML | 见下一节——支持矩阵太薄，等于把书的质量交给别人的实现 |

目标很具体：**一本扫描版的《数学分析》或《数值分析》，在 6 寸屏上字号随便调、公式是真公式、
能全文搜索、能划词批注、进度和另外几台设备同步。**

## 2. 核心决策：书里放 **LaTeX 源码**，而不是 MathML

这是一次**路线反转**。最初的前提是"只接受语义 MathML 作为公式载体"，并且做过完整调研：
在 MathML 前提下，现成路线（`latex2mathml` / `Temml` 作可插拔后端）比自建 Typst 路线更好，
Typst 的正确位置只是一个渲染后端加一个跨渲染校验器。

真正逼出反转的是两条实测事实：

1. **MathML 在 EPUB 里没人替你背书。** pdf-craft 自己的文档写着 MathML 在 EPUB 2.0 不受支持、
   "not all EPub readers can render the formula correctly"，并建议改用 SVG；
   支持矩阵实际是：Calibre 完整、Apple Books 部分（会忽略 `mrow`/`mtable`）、
   **Kindle/KF8 不支持**、微信读书直接忽略。
2. **XHTML 是严格 XML 解析。** `latex2mathml` 遇到畸形公式会产出不合法结构，浏览器糊得过去，
   EPUB 里一个未转义的 `<` 或 `&` 让**整本书打不开**——这就是"HTML 明明出得来、EPUB 打不开"的根因。

于是死结被看清了：**EPUB 的质量上限由阅读器决定，不由你的管线决定。** 继续在"怎么把公式编码得更
标准"上使劲，是在优化自己控制不了的那一半。

改路线之后：

| | 结果 |
|---|---|
| 公式 | **可搜索、可复制、可重排**（它就是一段正文） |
| 渲染质量 | 由 KaTeX 决定（Knuth TeX 的血统），**不再取决于哪个阅读器** |
| 降级 | 没有数学渲染器的阅读器显示 `\(P(x,y)\)` —— 略吵，**但完全可读**，不是空白也不是乱码 |
| 体积 | 行内公式平均几十字节；一张公式裁图几十 KB |
| 可逆性 | 源码原样留着，将来要转 MathML / SVG / 重新出 PDF 都行 |

### 关于"这样做很少见"

确实少见：**现成的 PDF→EPUB 工具几乎都输出 MathML**，把 LaTeX 留在 EPUB 里基本只见于
arXiv 源直接转制的书。选这条少数派路线，理由不是标准口味，是三个能用上的性质：

- **简洁**：`\[P(x,y)\mathrm{d}x + Q(x,y)\mathrm{d}y = 0\]` 一行 42 字节；同一条公式的
  MathML  Presentation 形式是 300~700 字节的结构化标记，而且**语义信息没多一分**——只是换了一种
  给人画、给人看的写法。
- **可检索**：公式在文本流里，`grep` 得到 `\int`，全文索引能索引到算子，读者在阅读器里搜
  "Taylor" 不会因为式子被打断而漏掉整段。
- **可被机器读**：这一条在 2026 年已经不是附加价值而是主要价值。LLM 读 LaTeX 是**母语**，
  读 MathML 是在啃标签树；读公式图片要动用视觉模型（见第 7 节，实测视觉模型在"判对错"上
  AUC 0.644 < 文本 0.715，图对图 0.409，但在"图→LaTeX 转写"上 25/25 全部编译通过）。
  只要库里存的是 LaTeX，"让模型帮我通读一本实变函数"就是一件直接可做的事；存 MathML 或图片，
  就得先付一次有损转换。

代价也很明确：**必须自带渲染器**。这就是这个 App 存在的理由——两半合起来才成立。

## 3. 架构

```
                    ┌─────────────────────────────────────┐
   扫描版 PDF ──────►│  pdf-craft + 远程 DeepSeek-OCR       │
   （无文字层）      │  （MinerU 作第二引擎，见第 6 节）     │
   数字版 PDF ──────►│                                     │
   （有文字层）      └──────────────┬──────────────────────┘
                                   │  .pcex 抽取归档 ← 契约层
                                   │  （公式=LaTeX 源码 + bbox + 图片 sha256）
                                   ▼
                    ┌──────────────────────────┐
                    │ 三层公式修复：texfix(文本) │
                    │ pcexlib(IR/块组装) · 渲染端 │
                    └────────────┬─────────────┘
              ┌──────────────────┼──────────────────┬───────────────┐
              ▼                  ▼                  ▼               ▼
       pcex2x --epub      pcex2x --tex     pcex2x --md    html_preview.py
       EPUB3（公式=LaTeX）  全书 .tex        .md            浏览器预览+失败清单
              │
              ├──────────────► embed_katex.py → KaTeX 自包含 EPUB（给别的阅读器用）
              │
              └──────────────► Liseur 分支：运行时注入 KaTeX（书保持纯净）
```

**`.pcex` 是整条链的地基**：它是 pdf-craft 的**抽取归档**，不是渲染产物——公式以 LaTeX 源码原样
保存（`\mathrm{d}x`、`Y_{1}(y)`），每个文本片段带 `bbox` + `page_index` 可以回溯原书版面做 QA，
图片按 sha256 独立存放。于是同一份归档能反复再渲染成任意后端，**改渲染参数不用重跑 OCR**
（0.1 秒/本 vs 十几秒/页，这个差别决定了后面所有实验的吞吐量）。

## 4. 公式在 EPUB 里的样子

```html
<!-- 行内 -->
<span class="math-inline">\(P(x,y)\)</span>

<!-- 块级：编号被拆出来单独右对齐 -->
<div class="math-block">
  <span class="math-body">\[P(x,y)\mathrm{d}x + Q(x,y)\mathrm{d}y = 0\]</span>
  <span class="eqno">(2.15)</span>
</div>
```

三个要点：

1. **用定界符包裹**，KaTeX 的 `renderMathInElement` 直接吃这套，零适配成本。App 侧支持的定界符是
   `$$…$$`、`\[…\]`、`\(…\)`、`\begin{equation|align|alignat|gather|CD}` 和
   `<script type="math/tex">`；**单个 `$…$` 刻意不支持**，因为 `$5 and not $6` 会吃掉整句正文。
2. **编号分离**。上游把编号留在 LaTeX 尾部（`\quad (2.15)`），管线把它拆成 `<span class="eqno">`，
   用 CSS grid 三栏实现"公式居中 + 编号贴右"。
3. **降级友好**：普通阅读器看到的是源码，可读。

踩过的两个坑值得单独记住：**注入的内联 `<script>` 里裸的 `i < nodes.length` 会让整本书打不开**
（XHTML 严格解析），必须 `//<![CDATA[ … //]]>` 包住；手写的 `<ol>` 嵌套状态机在层级回退时配错标签，
改成真正的递归。

## 5. 校验：先廉价筛，只把可疑项送贵模型

三层（`pipeline/verify.py`），设计原则是**唯一能规模化的形状**：

| 层 | 实跑在什么上面 | 职责 |
|---|---|---|
| **L0** | 纯本地，零调用 | 花括号配对、`\left…\right`、`\begin…\end`、孤立上下标、空分组、章节号误判、编号重复与跳号、正文引用存在性；**KaTeX 无头编译** |
| **L1** | `work/glm_scan.py` → Z.ai `glm-4.5-flash`（**$0**） | "这条 LaTeX 可疑吗"，一请求 160 条逐条 0~5 分，阈值分流 |
| **L2** | `work/vlm_fix_formulas.py` → `glm-4.6v-flash`（免费）／硅基流动／Google AI Studio 免费模型 | 带原图裁剪 + 上下文重识别并修正 |
| 内容层 | `work/sf_qa.py` → `Qwen/Qwen2.5-7B-Instruct` | 不可渲染的 markdown、多余/缺失符号、坏 LaTeX（**看得见文字，看不见"公式成了图"**） |

### 成本：额度就是预算

**现金支出 0。** OCR 用硅基流动 DeepSeek-OCR 的免费档，公式主筛用 Z.ai 免费 flash，视觉修复用
Z.ai 免费 flash 或 Google AI Studio 的免费模型，第二引擎 MinerU 是免费档 2000 页/天。
唯一走额度外余额的是 `sf_qa.py` 那条内容查错线，它吃账号里的 **¥16 聊天额度**（脚本注释原话：
"那个是免费档，本脚本走的是聊天额度（¥16），两条线互不抢"），并且默认挑最便宜的模型。

所以真正的约束不是钱，是**日请求额度**——几个参数的理由全在这里：

- `glm_scan` 一请求塞 **160 条**，不是判别力的选择：N 从 10 到 160，AUC 在 0.83~0.90 之间
  **不随批量衰减**（N=80 最好 0.899，N=160 是 0.877）；是因为免费档约 **1000 请求/天**，
  而全库 **128,532** 条公式按 N=80 要 1,607 个请求（超一天），N=160 只要 **803 个**（一天跑得完）。
- 免费档限的是**发起速率**不是并发数：并发 6 会撞 429（code 1302/1305），实测**并发 2 + 1.05s 间隔**稳定。
- **429 绝不能丢批次**：丢一批等于那 160 条变成"未判"，后面的统计就是在有偏子集上算的
  （标定时 N=20 那档未判 120/160，数字完全不可用）。所以失败批次**自动折半重试** 160→80→40→20，
  每本判完立刻落 `glm_out/scan_<stem>.json` 断点续跑。
- `verify.py` 里额度/鉴权类错误**不重试，直接中止本书剩余批次**——重试只是白烧额度。
- 修复线的多通道是**分密钥并行**（`zai.key` / `zai2.key` / `siliconflow.key` / `google.key`），
  否则两条线互相 429。

### 一处对不上的地方（别照抄代码注释）

`verify.py` 的文档头仍写着 L1 = Jev（TypeSafe System One）`~$0.007/书`、L2 = `~$0.5/书`。
那是 2026-09-20 设计阶段的估价，**从未按付费跑过**：Jev 实测**已弃用**——同批 240 条上它的
`correct` 维 AUC 只有 **0.688**（误伤 ≤20% 时召回 48.3%，而 `glm-4.5-flash` 是 **0.873 / 86.7%**），
再加上早期访问要排队、纯文本、不可靠计数、不生成文本。取代它的免费模型更强而且 $0。

另两条同源结论：**别让模型"在一组里选哪条错"**（k=8 命中率 0%，错误率的先验要写进指令），
以及视觉模型只做**已可疑项的二次分诊**、不独立担责（判对错 AUC 0.644 < 文本 0.715）。

L0 里最强的一项是 **KaTeX 无头编译**——它是真正的 parser，带完整宏表，比任何手写白名单可靠。
（最初手写了命令白名单，把 `\pm` `\mu` `\xi` `\gg` `\S` 全判成"残缺命令"，23 条误报，整项删掉。）
**编译检查的模式必须和阅读器一致**：`\[`→display、`\(`→inline；一律按 inline 编译会凭空造出
273 条假阳性。

L0 抓到的真问题有三类，且**互相印证**：编号识别错（正文引用的 `(2.11)` 在编号集合里不存在 +
跳号 + `(2.20)` 重复，两条独立检查指向同一批）、**公式被切成两半**（相邻两条的括号数正好互补，
需要的是合并而不是修正）、**非公式误判为公式**（`\S 2.3` 是章节号 §，该转成正文而不是渲染成公式）。

## 6. 规模化：让它自己跑三天

- **吞吐**（2026-09-22 重测，旧数字作废）：单本净速率中位 **5.87 s/页 ≈ 10.2 页/分**
  （串行逐页远端 OCR 约 15 s/页，是 `survey.py` 里那句实测注释；并发摊薄后才到 5.87）；
  `--jobs 6` → 19.7 页/分；`--jobs 12` → **43.7 页/分**。并发**近乎线性、没有服务端封顶**，
  18 逻辑核没跑满，瓶颈在网络往返——**该加 worker 就加**。全库按 43.7 页/分估算 ≈ 66 小时。
- **引擎**：默认 pdf-craft + 硅基流动 `DeepSeek-OCR`（免费、OpenAI 兼容）。MinerU 的 `vlm`
  引擎 0.62~0.68 s/页、准确率持平，但**没有裁剪图、没有页级续跑、2000 页/天额度**，
  片上限实测 200 页（官方文档写 600 是错的），所以只当第二引擎跑急件。
  `GET /api/v4/quota` 返 0 **不等于不能用**（那只是没有付费余额），必须实测提交。
  测速要换内容：同一文件二次提交命中服务端缓存，虚高 5 倍。
- **续航**（`work/autopilot.py`）：本机进程无法脱离会话，所以续航靠**每次调用幂等续跑**——
  抢锁（pid + 心跳，`--stale-min` 收僵尸锁）、小书优先、每轮 `--slice` 本、`--hours` 到点即退、
  清空后自动转 `--retry-failed`。中断只损失"在跑的几本"，因为是**页级可续**
  （`analysing_path` 必须持久，否则没有 `ocr/page_N.xml`）。
- **账本并发**：多个进程读-改-写同一个 manifest 会互相抹（后写抹前写）→
  `pipeline/manifest_lock.py` 用 OS 字节锁 + 锁内"重读→update→原子替换"。
  严格分区（`work/mineru_reserved.txt`）避免同一本书被两条线重复烧额度。
- **统计口径**（踩过才记住）：目录名是 `safe_stem(rel.replace("/","__"))` **≠ manifest 里的 rel**；
  全库统计从 `render_manifest.json` 取，`glob("*/*.epub")` 会漏一半；审计要遍历 `manifest`
  而不是 `render_manifest`；pcex 常并存 `X.pcex` / `X.degraded.pcex` / `X.nopage.pcex`，
  按体积挑会误选坏件虚报 50%~70%，**必须按后缀排除只量主件**。`page_indexes` 是 **1-based**。
  账本会说谎：`--render-only` 没有抽取事件，`degraded` 恒为 0 —— **判据要取自成品，不取自过程**。

## 7. 质量闭环：公式被当成图片插进来

**确定性判据，零误报、不用模型**：EPUB 里 `<img alt="公式">` ＝ 块级公式 OCR 失败后退成裁图；
`alt="插图"` ＝ 真插图。清点脚本 `work/formula_img_audit.py`。

实测 123 本：**公式成图 1,485 张，完全干净的书只有 14/123**。逐页小模型（`work/sf_qa.py`）
看不见这一层——它查的是内容层错误（不可渲染的 markdown、多余/缺失符号、坏 LaTeX），30 本报了
3,836 条。两层不能互相替代。

修复链路（2026-09-22 打通）反而是这条链路上最有意思的发现：**视觉模型"图 → LaTeX 转写"很强**，
实测 25/25 转写出的 LaTeX 全部通过 KaTeX 编译——而这些公式原本正是因为编译不过才退成图片的。
此前"视觉无用"的结论只适用于**判断对错**和**图对图**那两个任务，不是一回事。
质量分层（人工核对 5 张）：**大形态几乎全对**（`bmatrix`/`vmatrix`/`cases`/连分数/积分上下限/
`\tag` 编号都保住了），**细错在下标字符**（`I_9`→`I_v`、`T_m`→`T_a`）。

解法是**把原 OCR 的 LaTeX 当先验一起喂**：原 OCR 的字符往往是对的（只是结构坏了才编译不过），
纯看图反而会把 `T_m` 读成 `T_n`。提示词写明"字符参考初稿、结构以图为准"，两侧互补。
端到端不需要新写任何渲染器，管线早有机制：

```
Pcex(pcex) → chapters() → katex_failed_fids()      # 与渲染端 mark_failed_math 同一判据
  → 取「块级 + 有 asset_hash」= 会退成图的那批      # 《数值分析》dry-run 68 条，EPUB 里 alt="公式" 也是 68
  → p.read_asset(hash) 直接拿裁剪图                 # 不必从 EPUB 抽
  → work/corrections/<base_stem>.json = {fid: {latex, original}}
  → batch.py 自动加载该目录 → --render-only 重渲染    # original 必带：fid 是位置编号，IR 一变会整体错位
```

工具：`work/vlm_fix_formulas.py`（端到端，`--dry` 先看目标数）、`work/vlm_latex_ocr.py`（纯转写）、
`work/extract_formula_imgs.py`（备用）。两条硬教训：**提示词模板禁用 `str.format`**
（LaTeX 的 `{aligned}` 被当占位符，`KeyError`，踩了两次），以及**别去"修"故意的降级**——
`mark_failed_math` 的行为是"块级→裁剪原图、行内→丢乱码、修不好→留红字"，注释写着
"猜符号填进去是静默改坏，比红字坏得多"。

## 8. 和阅读器怎么接：两种接法都要

| 接法 | 用在哪 | 说明 |
|---|---|---|
| **EPUB 内嵌 KaTeX**（`embed_katex.py`，体积增大约 0.4 MB，只打包 `woff2`） | 在不具备注入能力的阅读器里读（Calibre / Edge / Apple Books） | 对 Marker/MinerU 的产出同样适用；不依赖任何阅读器实现 |
| **阅读器运行时注入**（本 App，`reader/MathTypesetting.kt`） | 自己的书保持纯净 | EPUB 里只有 LaTeX 源码，渲染器在 App 的 assets 里，全库共用一份 |

App 侧选注入是有理由的：Readium 靠"资源里有没有 `<style`"决定要不要挂它自己的样式表，
抢在前面改写资源会让一本无样式书**丢掉整个排字系统**；而且注入是唯一能覆盖**从服务器流式读取、
不落盘**的书的办法。早期 TexReader 原型选内嵌，理由是 `servedAssets` 这类 API 随版本变动而
"EPUB 引用自己的资源"永远成立——两个理由都成立，所以两种都留着。

一条排障经验：**非 Liseur 阅读器（Calibre / Edge / Apple Books）把公式显示成 `\(...\)` 源码，

## 10. 自己跑一遍

```bash
# 1) 抽取（一次，之后所有实验都在 .pcex 上做）
python E:/EPUB/pipeline/batch.py --only <书单.txt> --jobs 12 --log <log>

# 2) 只重渲染，不重新 OCR
python E:/EPUB/pipeline/batch.py --only <书单.txt> --render-only

# 3) L0 门禁 + 公式编译清单
python E:/EPUB/pipeline/check_math.py ...      # 与阅读器同一编译模式
python E:/EPUB/pipeline/check_epub.py ...      # XHTML 严格 XML / epubcheck

# 4) 要发给别人就读这个版本
python E:/EPUB/pipeline/embed_katex.py <in.epub> <out.epub>
```

Windows 侧的环境坑（都是真踩过）：长任务必须 `python -u` 否则日志 0 字节；`nohup … &` 会被工具壳
带走，长任务本身就得是后台任务的前台进程；python 不认 `/e/`，参数一律 `E:\`；读文件用 Read/Python
别用 `Get-Content`（mojibake）；网络**先实测再定代理**，直连 z.ai 是 000、siliconflow 直连通；
不建隔离虚拟环境，直接用系统 Python 装 pdf-craft。
